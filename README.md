# Билайн Бизнес — прототип планирования маршрутов инженеров

Прототип «интеллектуального сервиса планирования маршрутов инженеров»
(хакатон «Лидеры цифровой трансформации», кейс «Билайн Бизнес», см.
`3. Билайн Бизнес.pdf`). Четыре модуля от сырых данных до карты:
ETL (нормализация заявок с реальными координатами) → синтетические
инженеры → распределение заявок и построение маршрутов (VRPTW) → карта
маршрутов. Ниже — по разделу на каждый модуль, в порядке пайплайна.

## Установка

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
source .venv/bin/activate

pip install -r requirements.txt
```

## Запуск

```bash
python -m etl.run_etl
```

Флаги:
- `--no-network` — не ходить в Nominatim, использовать только
  fallback-координаты районов (быстро, для отладки без интернета).
- `--limit N` — обработать только первые N заявок.
- `--raw-dir`, `--reference-dir`, `--output-dir` — переопределить пути
  (по умолчанию `data/raw`, `data/reference`, `data/output`).

Первый прогон с реальным Nominatim идёт по политике 1 запрос/сек — на ~70
заявках это около минуты. Повторные прогоны используют диск-кэш
(`data/reference/geocode_cache.json`, не в git) и выполняются мгновенно.

## Синтетические инженеры

```bash
python -m engineers.generate_engineers
```

Генерирует `data/output/engineers.json` — 12 инженеров для региона
Восток: реальные имена бригад из `data/reference/historical/*.csv`,
координаты старта — из `data/output/offices.json` (нужно сначала
прогнать ETL), синтетические навыки/смена/транспорт со взвешенным
распределением (детерминировано по `--seed`, по умолчанию фиксирован —
повторный запуск даёт тот же результат).

Флаги: `--count` (по умолчанию 12), `--seed`, `--historical-dir`,
`--offices-path`, `--output`.

Формат записи:
```json
{
  "id": "eng_01",
  "name": "Капитанчук Александр",
  "start_lat": 55.7004508, "start_lon": 37.7494938,
  "shift_start": "10:00", "shift_end": "18:00",
  "skills": ["Локальные работы", "Аварийные работы"],
  "vehicle": "Пешеход"
}
```

Допущение: имена реальные (для правдоподобности), но навыки/смена/
транспорт — полностью синтетические, в исходных данных их нет вообще.

## Распределение заявок и маршруты

```bash
python -m routing.run_distribute
```

Строит матрицы времени/расстояния через OpenRouteService (по одному
запросу на вид транспорта, встречающийся у инженеров) и решает VRPTW
(`ortools`) с тремя группами ограничений ТЗ §2.2 (квалификация, время,
ресурс/транспорт). Пишет `data/output/assignment.json` и печатает
метрики (`engineers_used`, `total_distance_km`, `orders_assigned`,
`orders_unassigned`) в stdout.

Требует `ORS_API_KEY` в `.env` — бесплатный ключ регистрируется на
[openrouteservice.org](https://openrouteservice.org/dev/#/signup)
(Dashboard → Create token). Без ключа, без сети или с флагом
`--no-network` модуль использует haversine-фолбэк (прямая линия ×
коэффициент непрямоты дорог, средняя скорость по виду транспорта) —
пайплайн не падает, но расстояния менее точные.

Флаги:
- `--no-network` — не ходить в OpenRouteService, сразу haversine-фолбэк.
- `--time-limit N` — лимит времени решателя OR-Tools в секундах
  (по умолчанию 10).
- `--orders-path`, `--engineers-path`, `--offices-path`, `--output` —
  переопределить пути к входам/выходу (по умолчанию
  `data/output/{orders,engineers,offices}.json` и
  `data/output/assignment.json`).

Реальный прогон на текущих данных (66 заявок, 12 инженеров, 1 офис):
```json
{
  "engineers_used": 11,
  "total_distance_km": 148.63,
  "orders_assigned": 54,
  "orders_unassigned": 12
}
```

Если исполнителей физически не хватает на все заявки, штраф за
неназначенную заявку различается по приоритету её типа (не только по
самому факту «Срочная»/«Обычная»): `Авария > Подключение/Дозаказ >
Локальные работы` — это прямой ответ постановщика в Q&A на «какие
заявки приоритетнее при нехватке ресурсов». Наши данные не различают
«Подключение» и «Дозаказ» отдельно (ETL схлопывает оба в один навык
«Работы на подключение и дозаказы» ещё на этапе нормализации) — оба
идут одним, средним по величине штрафом; «Локальные работы» — ближайший
по смыслу аналог «Ремонта» из ответа. Реализовано в
`routing/solve.py::UNASSIGNED_PENALTY_BY_SKILL`, действует только на
исходном статическом распределении (`routing.run_distribute`) — в
перепланировании (`routing.replan`) приоритет отдельной срочной заявки
и так реализован явно (вытеснение ещё не начатой обычной, см. раздел
«Перепланирование»).

Бесплатный тариф ORS Matrix API ограничивает один запрос 3500 маршрутами
(`sources × destinations`), а точек в наборе 67 (офис + 66 заявок) — при
запросе всей матрицы разом это 67² = 4489 > 3500. Поэтому
`routing/distance_matrix.py` разбивает запрос на квадратные блоки по
`sources`/`destinations` (размер блока — `floor(sqrt(3500))`), собирает
блоки в одну матрицу и кэширует её целиком. На всех 67 точках матрица для
профилей `car`, `foot` и `bike` строится через OpenRouteService
(`source: "ors"`), то есть расстояния в маршрутах (`distance_km`)
посчитаны по реальным дорогам, а не по haversine-приближению. Линии на
карте (`routemap/build_map.py`) тоже рисуются по дорогам — через ORS
Directions API, отдельным запросом; см. раздел «Карта маршрутов».

OR-Tools — метаэвристика с лимитом времени, а не точный решатель, поэтому
числа немного колеблются от запуска к запуску даже на одних и тех же
данных.

Формат `data/output/assignment.json` (пример маршрута и пример отказа —
из этого же прогона; у `unassigned`-заявок причина различается в
зависимости от того, почему именно назначение невозможно — нет навыка,
нет транспорта, нет пересечения смены и окна, работа не влезает в окно
и смену, инженер не успевает доехать до закрытия окна, или подходящие
инженеры есть, но заявку не удалось встроить в их маршруты — они заняты
другими заявками):
```json
{
  "routes": [
    {
      "engineer_id": "eng_01",
      "engineer_name": "Прокопенко Вячеслав",
      "stops": [
        {
          "order_id": "32807",
          "arrival": "10:00",
          "travel_min": 3,
          "distance_km": 1.71,
          "reason": "Один из 5 подходящих инженеров по навыку и времени — выбран по критерию маршрута (минимум инженеров/пробега)"
        }
      ],
      "total_distance_km": 54.81
    }
  ],
  "unassigned": [
    {
      "order_id": "74198",
      "reason": "Работа занимает 70 мин — ни один подходящий инженер не успевает выполнить её до конца смены в пределах окна 20:00–22:00"
    }
  ],
  "metrics": {
    "engineers_used": 11,
    "total_distance_km": 148.63,
    "orders_assigned": 54,
    "orders_unassigned": 12
  }
}
```

## Карта маршрутов

```bash
python -m routemap.build_map
```

Читает `data/output/orders.json`, `data/output/engineers.json`,
`data/output/offices.json` и `data/output/assignment.json`, строит
статичную HTML-карту (Folium/Leaflet + OpenStreetMap) и печатает
`Карта сохранена: data\output\route_map.html` (или `/`-путь на
не-Windows) в stdout.

Флаги — те же пути к входам, что и у `routing.run_distribute`, плюс путь
к выходному файлу:
- `--orders-path`, `--engineers-path`, `--offices-path`,
  `--assignment-path` — переопределить входы (по умолчанию
  `data/output/{orders,engineers,offices,assignment}.json`).
- `--output` — переопределить путь к результату (по умолчанию
  `data/output/route_map.html`).
- `--no-network` — не ходить в OpenRouteService за геометрией, сразу
  рисовать прямые линии (тот же смысл, что у `routing.run_distribute`).
- `--comparison-path` — путь к `comparison.json` для блока сравнения в
  легенде (по умолчанию `data/output/comparison.json`); если файла нет,
  блок просто не появляется, карта строится как обычно.

Результат — один самодостаточный HTML-файл. Открывать лучше через
локальный сервер: OpenStreetMap блокирует тайлы (403 «Access blocked») для
страниц, открытых как `file://`, а с `http://localhost` пропускает:
```bash
python -m http.server 8000 --directory data/output
# затем http://localhost:8000/route_map.html
```

Содержимое карты:
- Маркер офиса (стартовая точка инженеров региона), отдельной иконкой.
- Для каждого инженера с непустым маршрутом — пронумерованные маркеры
  остановок (`1`, `2`, …, в порядке визита) своим цветом, во всплывающей
  подсказке — номер заявки, имя инженера, время прибытия, пробег до
  точки, причина назначения.
- Линии маршрута того же цвета, что маркеры инженера, между
  последовательными остановками (и от офиса до первой).
- Серые маркеры неназначенных заявок, во всплывающей подсказке — номер
  заявки и причина отказа.
- Легенда под картой (HTML-таблица в том же файле): сводные метрики
  (`engineers_used`, `total_distance_km`, `orders_assigned`,
  `orders_unassigned`), по блоку на инженера с списком остановок и
  причин, блок неназначенных заявок с причинами, список инженеров без
  назначений.

Геометрия маршрутов, полученная через ORS Directions, кэшируется в
`data/reference/routing_cache.json` (ключи с префиксом `geometry:`).

Известные допущения:
- Линия маршрута — реальная геометрия дороги через ORS Directions API
  (`DistanceMatrixBuilder.fetch_geometry`), когда сеть/ключ доступны;
  при недоступности — прежнее приближение (прямая между точками), карта
  не падает.
- Цифры пробега рядом с маршрутом (легенда/попапы) по-прежнему берутся
  из `assignment.json` (Matrix API, использовано в самой оптимизации) и
  могут отличаться от точной длины нарисованной линии на уровне
  округления ORS — это разные API одного сервиса, не расхождение данных.
- Общественный транспорт визуализируется как пеший маршрут (нет
  реального профиля общественного транспорта ни у ORS, ни у какого-либо
  бесплатного альтернативного сервиса для Москвы).
- Карта статична: один прогон CLI → один HTML-файл. Изменения в данных
  требуют повторного запуска `python -m routemap.build_map`.
- OSM-тайлы подгружаются браузером при просмотре, не при генерации — для
  просмотра карты (не только легенды) нужен интернет в момент открытия
  файла.
- Если `assignment.json` устарел (ссылается на заявку, которой уже нет
  в `orders.json` — например, `orders.json` перегенерировали после
  сборки `assignment.json`), модуль явно падает с понятной ошибкой,
  подсказывающей перегенерировать `assignment.json`
  (`python -m routing.run_distribute`), а не тихо строит карту с
  пропущенными точками.

## Сравнение с базовым вариантом

```bash
python -m routing.compare_baseline
```

Считает на одних и тех же данных и оптимизированный (OR-Tools) план, и
базовый — жадный алгоритм без оптимизации, реализованный буквально по
формулировке ТЗ §2.3: заявки и инженеры перебираются в порядке входных
данных, первый подходящий по всем трём группам ограничений инженер
получает заявку, порядок посещения = порядок назначения. Оба плана
считаются заново в одном процессе на одних и тех же матрицах —
`assignment.json` не читается, чтобы сравнение было честным (без
дрейфа между старым прогоном OR-Tools и свежим базовым). Пишет
`data/output/comparison.json` (оба полных плана + сводка из 4 метрик) и
печатает читаемую таблицу в stdout.

Флаги — те же, что у `routing.run_distribute`: `--orders-path`,
`--engineers-path`, `--offices-path`, `--output` (по умолчанию
`data/output/comparison.json`), `--no-network`, `--time-limit`.

Реальный прогон на текущих данных:
```
                          Оптимизация   Базовый вариант
Задействовано инженеров:           11                12
Суммарный пробег, км:          148.63            138.21
Назначено заявок:                  54                28
Не назначено заявок:               12                38
```

Обратите внимание: у базового варианта пробег ниже, но это не
преимущество — он просто назначает намного меньше заявок (28 против 54)
почти тем же числом инженеров (12 против 11). Меньше поездок — меньше
суммарный километраж, а не более эффективный маршрут. Это и есть
демонстрация ценности оптимизации: OR-Tools закрывает почти в 2 раза больше
заявок сопоставимым числом исполнителей.

Если `data/output/comparison.json` существует на момент запуска
`python -m routemap.build_map`, легенда карты дополнительно показывает
эти 4 метрики side-by-side (необязательный шаг — карта строится и без
предварительного запуска сравнения).

## Перепланирование

```bash
python -m routing.replan --event-path <event.json>
```

Применяет **одно** событие перепланирования (ТЗ §2.1.6/§2.4/§2.4.2)
точечным патчем поверх уже посчитанного `data/output/assignment.json` —
не пересчитывает план с нуля, чтобы результат было легко объяснить (ТЗ
§2.4.2: «наглядно показать, что изменилось»). Три типа события:

- `new_urgent_order` — новая срочная заявка (нужен полный набор полей
  заявки прямо в событии — она не должна существовать в `orders.json`).
  Заявку нельзя поставить так, будто инженер выехал к ней раньше, чем
  произошло само событие. Срочная ставится на самое раннее допустимое
  время (при равенстве — с минимальным добавленным пробегом), обычная — с
  минимальным добавленным пробегом. Если срочная никуда не влезает без изменений,
  разрешено снять с маршрута ровно одну ещё не начатую заявку с
  приоритетом «Обычная» (без каскадов) и поставить срочную на её место
  (ТЗ §2.4.1: срочная имеет приоритет при конфликте) — снятая заявка
  сама пытается встать в другое место, иначе становится неназначенной.
- `cancel_order` — отмена существующей заявки по `order_id`.
- `engineer_unavailable` — инженер стал недоступен по `engineer_id`.
  Необязательные поля `from` и `until` (`HH:MM`) задают интервал
  недоступности, например
  `{"type": "engineer_unavailable", "event_time": "09:00", "engineer_id": "eng_01", "from": "11:00", "until": "12:30"}`.
  Заявки инженера, которые стартуют внутри интервала, переходят к
  другим (срочные первыми); остальные остаются за ним, но не начинаются
  внутри интервала (сдвигаются на его конец, никогда не позже исходного
  времени). Работа, начатая до интервала, доделывается. Без `from`
  интервал начинается в `event_time`, без `until` длится до конца смены
  (прежнее поведение). В Streamlit-интерфейсе объявленные интервалы
  запоминаются в сессии и учитываются следующими событиями.

Формат события — `{"type": ..., "event_time": "HH:MM", ...}`, примеры
каждого типа — в `data/output/demo_event*.json`.

Остановки, время прибытия на которые уже раньше `event_time`,
считаются свершившимся фактом и не трогаются — патч работает только с
ещё не наступившим «хвостом» дня. Новая/осиротевшая заявка вставляется
в самую дешёвую по добавленному пробегу открытую позицию среди всех
подходящих инженеров (не только уже занятых).

Пишет `data/output/replan.json` — **отдельный файл**, не перезаписывает
`assignment.json` (есть и «до», и «после» одновременно).
`routes`/`unassigned`/`metrics` лежат прямо на верхнем уровне файла
(рядом с `event`/`diff`), поэтому карту по новому плану можно построить
без каких-либо изменений в `build_map.py`:
```bash
python -m routemap.build_map --assignment-path data/output/replan.json --output data/output/replan_map.html
```
(работает для `cancel_order`/`engineer_unavailable`; для
`new_urgent_order` карта не отрисует саму новую заявку — её нет в
`orders.json`, см. «Известные допущения» ниже).

Флаги: `--event-path` (обязательный), `--orders-path`,
`--engineers-path`, `--offices-path`, `--assignment-path` (по умолчанию
`data/output/assignment.json`), `--output` (по умолчанию
`data/output/replan.json`), `--no-network`, `--cache-path`.

Пример на текущих данных (`data/output/demo_event.json` — отмена заявки
`76678` у `eng_01` в 11:00):
```
Изменения после перепланирования:
  - 76678 отменена
```
Сценарий `new_urgent_order` (`data/output/demo_event_urgent.json`): новая
срочная заявка рядом с офисом встаёт в маршрут `eng_04` с прибытием в 11:08
(запуск с `--no-network`; с реальной матрицей ORS время может немного отличаться):
```
Изменения после перепланирования:
  + 999 -> eng_04 (прибытие 11:08)
```

Известные допущения:
- Точечный патч, не глобальная переоптимизация — план после события
  может быть не идеально оптимален относительно чистого пересчёта с
  нуля, зато диф маленький и понятный.
- Одно событие за вызов. Ничто не мешает применить `routing.replan`
  второй раз к `replan.json` как к новому «текущему» плану, если
  понадобится продемонстрировать несколько событий подряд.
- Уже неназначенные до события заявки не переоцениваются заново — патч
  пересматривает только напрямую затронутые событием заявки.
- Карта по `replan.json` не отрисует саму новую заявку для события
  `new_urgent_order` — она существует только внутри события, её нет в
  `orders.json`, откуда `build_map.py` берёт координаты остановок.
  Для `cancel_order`/`engineer_unavailable` карта строится полностью
  (там все заявки уже есть в `orders.json`).
- Остановки, время прибытия на которые раньше `event_time`
  («замороженный префикс»), никогда не пересчитываются: в итоговый план
  они попадают из `assignment.json` как есть. Хвост маршрута, которого
  событие не коснулось, тоже берётся без пересчёта — чтобы результат не
  зависел от источника матрицы расстояний (`data/reference/routing_cache.json`
  лежит в репозитории: там матрицы расстояний для исходного набора точек и
  геометрия маршрутов исходного плана, поэтому отмена и недоступность
  инженера работают без сети и без обращения к ORS; новая точка срочной
  заявки требует нового запроса к ORS, без него используется haversine). Пересчитывается
  только хвост, в котором реально вставили или сняли остановку.
- Если такой хвост при пересчёте по другой матрице (например, фолбэк
  вместо ORS) перестаёт быть допустимым, `apply_event`/CLI откажут с
  понятной ошибкой (`ValueError`), а не выдадут неверный план. На данных
  проекта так бывает при отмене части заявок `eng_05`/`eng_12` в
  `--no-network` (узкие окна), если кэша нет. Матрица берётся из кэша (`--cache-path`,
  по умолчанию `data/reference/routing_cache.json`) прежде фолбэка, так что
  при одном и том же кэше для исходного плана и для перепланирования
  расхождения не возникает. Известное ограничение.

## Интерфейс перепланирования (Streamlit)

```bash
streamlit run ui/replan_app.py
```

Открывает страницу в браузере (`http://localhost:8501`). Слева — панель
события: срочная заявка (адрес геокодится через Nominatim; не найден —
понятная ошибка, план не меняется), отмена заявки, инженер недоступен,

к текущему плану — события можно применять подряд; «Сбросить» возвращает
исходный `data/output/assignment.json`. Справа — диф, таблица метрик
до/после и вкладки с картами «После»/«До». В отличие от CLI, срочная
заявка здесь рисуется на карте.

Нужен предварительно посчитанный `data/output/assignment.json`
(`python -m routing.run_distribute`). Состояние живёт в сессии страницы:
срочные заявки, добавленные в интерфейсе, не пишутся в `orders.json`.

## Структура данных

- `data/raw/vostok_synthetic.csv` — заявки для планирования (без
  назначенного исполнителя). Схема: `Заявка;Тип заявки BK;Тип заявки HD;
  Начало;Окончание;Район;Адрес;Подключение;Гигабитное подключение`.
  Последняя строка файла — не заявка, а адрес офиса (стартовая точка
  инженеров региона), извлекается в `data/output/offices.json`.
- `data/reference/norms.json` — нормативы длительности/навыка/приоритета
  по `Тип заявки BK`. `duration_on_site_min = tech_min + docs_min`;
  `road_min` — справочное значение, НЕ используется как константа, реальное
  время в пути ETL не считает (это задача алгоритма маршрутизации по
  координатам заявок).
- `data/reference/geocode_fallback.json` — примерные центроиды районов,
  используются, только если Nominatim недоступен/не нашёл адрес.
- `data/reference/historical/*.csv` — историческая («контрольная»)
  раскладка реального дня, с колонками `Статус BK` и `Бригада`. Только
  ориентир, совпадение с ней не требуется. Статусы не фильтруются — файл
  содержит все строки, включая «Отменена»/«Выполнена», как было в реальности.

## Формат результата — `data/output/orders.json`

Список объектов вида (реальная запись из `data/output/orders.json`
последнего прогона; `lat`/`lon` — фактические координаты от Nominatim,
`geocode_source` может быть и `cache`, если адрес уже встречался в
предыдущем прогоне — координаты от этого не хуже, просто взяты из
диск-кэша вместо повторного сетевого запроса):
```json
{
  "id": "74198",
  "address": "Город Москва, пр-кт.Волгоградский, д. 128 к 5",
  "district": "Кузьминки",
  "lat": 55.700846, "lon": 37.7822191, "geocode_source": "cache",
  "duration_min": 70,
  "window_start": "20:00", "window_end": "22:00", "date": "2026-08-17",
  "priority": "Обычная",
  "required_skill": "Работы на подключение и дозаказы",
  "required_transport": null,
  "gigabit": false,
  "source_file": "vostok_synthetic.csv"
}
```

`geocode_source` — один из `nominatim`, `cache`, `fallback:<район>`,
`fallback:default`.

`data/output/historical_reference.json` — та же схема плюс `status` и
`historical_brigade`, для исторических заявок.

`data/output/offices.json` — стартовые точки инженеров по регионам:
`{"source_file", "address", "lat", "lon", "geocode_source"}`. У офисного
адреса нет района (`OfficeInfo` не хранит `district`), поэтому если
Nominatim для него недоступен, фолбэк уходит сразу на глобальный дефолт
(центр Москвы), а не на районный центроид, как у обычных заявок.

## Известные допущения

- `required_transport` всегда `null` — в исходных данных нет ни одного
  сигнала для требуемого типа транспорта; поле оставлено для совместимости
  со схемой из ТЗ и заполняется дальше по пайплайну при необходимости.
- Истинная региональная принадлежность `control_set_a.csv`/
  `control_set_b.csv` не восстановлена — исходные файлы были перепутаны до попадания в эту
  структуру, region-метка была утеряна безвозвратно.
- Время в пути между точками маршрута (кроме geo-координат) — ответственность
  модуля распределения/маршрутизации, не этого ETL.
- Нормализация адреса перед запросом к Nominatim (`geocode.py`,
  `normalize_address_for_nominatim`) раскрывает распространённые сокращения
  (ул., пр-кт., пер., наб., б-р., ш., обл.) и убирает шумовые слова
  («Город», «д.», «кв.», «стр.», «пгт.»), проверено на реальных адресах
  датасета. Не все возможные варианты адресов покрыты (например, некоторые
  типы улиц вроде «проезд» надёжнее находятся в суффиксной форме, а не
  префиксной) — непокрытые случаи корректно деградируют в fallback по
  району, а не падают с ошибкой.
- Инженеры (`data/output/engineers.json`) — синтетические: реальные
  только имена (из исторических данных), привязка имени к
  навыкам/смене/транспорту — решение команды, не выведено из данных.
- Общественный транспорт — geometry пешего маршрута + отдельная средняя
  скорость (~15 км/ч), не настоящий транзитный маршрут (для него нужен
  отдельный GTFS-сервис уровня Google Directions, недоступный бесплатно).
- Коэффициент непрямоты дорог в haversine-фолбэке (~1.3) и средние
  скорости по видам транспорта — приближение для случая недоступности
  ORS, не заявлены как точный расчёт.
- Лексикографический приоритет метрик (сначала число инженеров, потом
  пробег) реализован через большой фиксированный вес, а не через
  строгую двухэтапную оптимизацию — для целей хакатона этого достаточно
  и ТЗ явно не требует доказывать математический оптимум.
